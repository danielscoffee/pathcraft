# Phase 1.0 Ecosystem Design

## Scope

Complete Phase 1.0 at PathCraft's prototype maturity with four concrete ecosystem surfaces:

1. task-oriented Go SDK documentation backed by compiling external-package examples;
2. browser JavaScript bindings built with Go's `js/wasm` target;
3. a versioned protobuf/gRPC API for coordinate street routes and multimodal journeys;
4. documented, tested compile-time plugins, without replacing the registry already shipped.

Phase completion means these surfaces build, run against the existing engine, and state their limits. It does not mean packaged releases, npm publication, stable compatibility guarantees, remote plugin execution, production API security, or feature parity between every transport.

## Chosen architecture

Keep transport adapters thin and call `pkg/pathcraft/engine` directly. Add no shared service framework: HTTP, gRPC, and WASM have different request formats and lifecycle constraints, while engine methods already provide the common behavior.

Two heavier alternatives are rejected:

- A transport-neutral service layer would mostly mirror engine request/result structs and add mapping without current reuse value.
- Proxying JavaScript through HTTP would not be a WASM binding and would reintroduce server deployment into browser use.

Generated protobuf types live in `api/pathcraft/v1`; gRPC implementation remains internal. Browser glue lives in a `js/wasm` command plus one small ES module. Existing plugin interfaces and registry remain the extension mechanism. Phase 1.0 proves and documents them instead of adding dynamic `.so`, subprocess, WASM, or network plugin runtimes.

## Go SDK

`pkg/pathcraft/engine` remains the primary SDK. Documentation covers:

- creating and configuring an engine;
- loading OSM from a path or plain XML reader;
- loading GTFS directories;
- node, coordinate, transit, and multimodal routing;
- graph cache lifecycle and concurrent read-only query contract;
- registry-backed pipelines and custom compile-time plugins.

A new reader-based OSM loader avoids temporary files for embedded callers and gives WASM a native ingestion path. It hashes bytes while parsing, then uses the same graph construction and contraction pipeline as path loading. File loading still supports `.osm.gz`; reader loading accepts plain OSM XML only.

External-package examples compile against public imports and run on the tracked small OSM fixture. Documentation must not imply semantic-version stability while the project is pre-release.

## JavaScript/WASM binding

Compile `cmd/pathcraft-wasm` with `GOOS=js GOARCH=wasm`. It registers three synchronous low-level functions under `globalThis.pathcraftWasm`:

- `loadOSM(xml)` parses plain OSM XML and publishes a contracted graph;
- `route(requestJSON)` solves a coordinate route for walk, bike, or car;
- `stats()` returns graph statistics.

All low-level calls return a JSON envelope so Go errors cross the JS boundary without panics. `sdk/js/pathcraft.mjs` loads a Wasm byte source or URL, unwraps envelopes, and exposes ordinary JavaScript objects. Caller supplies matching Go `wasm_exec.js`; runtime and compiled module must use the same Go major version.

No fetch runs inside a `syscall/js.FuncOf` callback because blocking that callback also blocks JavaScript's event loop. Caller fetches OSM text before invoking `loadOSM`. GTFS, workers, streaming input, cancellation, npm packaging, and checked-in `.wasm` binaries stay out of scope. Large datasets run synchronously on browser main thread; workers are future work when measured UI blocking warrants them.

## gRPC API

Define `pathcraft.v1.RoutingService` in protobuf with:

- `Route`: coordinate-to-coordinate street route, per-request walk/bike/car mode, optional coordinates;
- `Journey`: timed coordinate multimodal result with typed legs.

Use generated protobuf messages and generated Go client/server interfaces. Durations cross the API as integer seconds, avoiding Go-specific `time.Duration`. Coordinates use explicit latitude/longitude messages. Enum zero values choose walking defaults.

Server validates finite coordinate ranges, modes, required departure time, and bounded stop-candidate counts before engine calls. Invalid input maps to `InvalidArgument`; unavailable engine data maps to `FailedPrecondition`; unsolved routes map to `NotFound`; unexpected failures map to `Internal`. Standard gRPC health service reports `SERVING` after registration.

`pathcraft grpc` loads OSM and optional GTFS before listening. Default address is loopback (`127.0.0.1:9090`) to avoid accidental network exposure. TLS, authentication, authorization, quotas, reflection, streaming, and public-internet hardening remain explicit non-goals. Users choosing a non-loopback address own perimeter security.

## Plugin system

Current compile-time registry already satisfies Phase 1.0 plugin scope:

- public algorithm, loader, exporter, cost model, and logger interfaces;
- deterministic duplicate rejection and sorted discovery;
- built-in adapters registered by blank import;
- isolated registries for tests;
- end-to-end loader → algorithm → exporter evidence.

No plugin code rewrite is needed. SDK documentation links authoring steps and states compile-time constraints. Dynamic loading remains a non-goal until a concrete deployment requires process isolation or runtime installation.

## Validation

Test-first evidence must prove:

- reader-loaded OSM routes match file-loaded behavior and malformed XML returns an error;
- WASM bridge loads XML, routes, validates JSON/modes/coordinates, and reports unloaded state;
- real `js/wasm` build starts under Node with matching `wasm_exec.js` and crosses the JS boundary;
- generated gRPC client reaches a `bufconn` server, receives a route, sees validation status codes, and reads standard health status;
- Go SDK examples compile and run;
- existing registry and plugin pipeline tests remain green;
- protobuf regeneration leaves no diff.

Run focused package tests first, then Go tests, race detector, vet, native build, explicit WASM build/smoke, frontend tests/lint/build, LSP diagnostics, and fresh read-only correctness/security review.

## Honest limits

Phase 1.0 delivers prototype ecosystem entry points, not stable releases. gRPC defaults to local plaintext and has no auth. WASM supports street routing only, uses plain XML input, and blocks its worker or browser thread while parsing/routing. Generated APIs may change before v1 release. Plugins are linked at compile time. Existing GTFS calendar/realtime, geocoding, traffic, production controls, packaging, and horizontal scaling gaps remain.
